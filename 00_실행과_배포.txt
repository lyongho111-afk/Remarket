1. Windows에서 바로 실행
ZIP 전체를 새 폴더에 풀고 실행하기.cmd를 엽니다.
학생 화면 http://localhost:8080/sales/selectAll
사장센터 http://localhost:8080/owner/
관리자 화면 http://localhost:8080/admin/
같은 포트에서 이전 버전이 실행 중이면 이전 서버를 먼저 종료합니다.
이 실행 방식은 기존 발표용 모드입니다. 예시 계정이 들어 있고 재시작 시 초기화됩니다.

2. 상시 서버와 도메인을 확보한 뒤 배포
Docker와 Docker Compose가 있는 단일 Linux 서버를 기준으로 준비했습니다.
압축 해제한 campus-remarket 디렉터리에서 .env.example을 .env로 복사하고 다음 항목을 입력합니다.
  CAMPUS_DOMAIN         소유한 도메인의 호스트 이름(https:// 없이 입력)
  CAMPUS_DB_PASSWORD    새 DB의 고유 비밀번호. 재배포 시에도 같은 값을 사용
  SMTP_* / MAIL_FROM    실제 가입 인증 메일을 사용할 때 메일 제공자 설정
도메인의 A 레코드를 서버의 공인 IPv4에 연결하고 IPv6를 사용할 경우 AAAA도 연결합니다.
외부에서 80/TCP와 443/TCP로 접속할 수 있게 한 뒤 아래 명령을 실행합니다.
  docker compose config --quiet
  docker compose up --build -d
  docker compose logs --tail 80 app https
Caddy가 HTTPS 인증서를 발급합니다. 공유 주소는 https://설정한도메인/sales/selectAll 입니다.
배포용 hosted 프로필은 예시 계정을 자동 생성하지 않습니다. 학교 목록과 게시판 카테고리만 초기화합니다.
H2 파일 DB와 업로드 파일은 campus_data 볼륨에 저장합니다. DB 파일은 서버 한 대, 앱 한 인스턴스에서 사용합니다.
업데이트 전에는 앱을 정지하고 볼륨을 백업합니다. docker compose down -v 는 볼륨을 삭제합니다.
이 배포 구성은 도메인 연결 전까지 로컬 준비 상태입니다.

3. 토스 카드 테스트와 웹훅
토스페이먼츠가 발급한 동일 상점의 테스트 클라이언트 키와 시크릿 키를 .env의
TOSS_CLIENT_KEY, TOSS_SECRET_KEY에 넣고 TOSS_PAYMENT_MODE=TEST로 둡니다.
키를 넣은 뒤 docker compose up -d 로 앱 환경을 갱신합니다.
개발자센터에서 PAYMENT_STATUS_CHANGED 이벤트를 아래 HTTPS 주소에 등록합니다.
  https://설정한도메인/api/payments/webhook/toss
테스트 구매자로 상품을 예약하고 ‘거래 지도 · 결제 확인’에서 토스 테스트 결제를 엽니다.
같은 주문번호와 금액으로 결제사 승인, 구매자 화면의 상태, 토스 테스트 거래내역 세 곳을 대조합니다.
웹훅을 재전송해도 승인·취소가 한 번만 반영되는지 확인합니다. 이때 테스트 카드에는 실제 대금이 청구되지 않습니다.
자동화 검증은 모의 결제사 응답으로 진행합니다. 실제 가맹점 테스트 승인과 웹훅 전달 확인은 키와 공개 URL이 생긴 뒤 진행합니다.
운영 결제는 가맹 계약 및 테스트 완료 후 운영 클라이언트/시크릿 키, TOSS_PAYMENT_MODE=LIVE,
ENABLE_LIVE_PAYMENTS=true를 모두 명시해야 활성화됩니다. 운영에 연결하기 전 가입, 취소, 환불,
결제사 거래내역 대조 및 모니터링 절차를 점검하고 테스트 DB와 운영 DB를 분리합니다.
결제 취소는 현재 결제사 측에서 발생한 결과를 수신해 반영합니다.
공식 안내: https://docs.tosspayments.com/guides/v2/webhook

4. 기존 모의 에스크로 시연 (일반 테스트 카드 결제)
구매자와 판매자는 서로 다른 학생 계정을 사용합니다.
  ① 구매자가 예약하고 테스트 카드 결제를 승인합니다.
  ② 거래의 ‘에스크로 · 모의 정산’에 보관 금액이 표시됩니다.
  ③ 구매자가 ‘물품 수령 · 구매 확정’을 누릅니다.
  ④ 판매자가 해당 거래에서 ‘판매자 모의 정산 기록’을 누릅니다.
승인된 테스트 결제의 주문·금액이 일치해야 장부가 생성됩니다. 미결제 대면 완료 또는 LIVE 영수증에는
모의 정산이 발생하지 않습니다. 부분/전액 취소 시 확인된 잔액을 표시합니다.
실제 자금을 맡거나 은행 계좌로 보내는 기능은 없습니다. 실제 도입 전 결제사와 대면 직거래 에스크로,
개인 판매자 등록·지급대행, 취소/분쟁 절차를 협의해야 합니다.

5. 소스 수정 후 재빌드
JDK 25를 설치하고 프로젝트 루트에서 Windows는 gradlew.bat test bootJar,
Linux/macOS는 sh gradlew test bootJar를 실행합니다. build/libs에 생성된 실행 JAR를
Windows 실행본을 갱신하려면 app/campus-remarket.jar로 복사합니다. Docker 이미지는 gradle과 src/main에서 직접 빌드하므로 사전 빌드된 JAR가 필요하지 않습니다.

6. 토스 테스트 상점을 실제로 연결할 때
팀 계정으로 https://developers.tosspayments.com/my/api-keys 에 로그인하고, 같은 테스트 상점의
API 개별 연동 키를 선택합니다. 클라이언트 키와 시크릿 키는 호스팅 비밀 설정 또는 개인 .env에만 보관합니다.
일반 테스트 카드 결제는 TOSS_PAYMENT_MODE=TEST, ENABLE_LIVE_PAYMENTS=false로 실행합니다.
고정 HTTPS가 준비되면 /api/payments/webhook/toss 에 PAYMENT_STATUS_CHANGED 를 등록하고,
테스트 주문번호로 개발자센터의 승인 기록, 웹훅 전달 성공, 구매자 화면의 상태를 함께 확인합니다.
실거래 키를 사용하거나 실제 지급 요청을 보낼 필요가 없습니다.

토스가 해당 상점의 에스크로 테스트 사용을 허용했다면 TOSS_TEST_ESCROW_ENABLED=true를 추가합니다.
별도 에스크로 웹훅 /api/payments/webhook/toss-escrow 에 escrow.changed와 delivery.changed를 등록합니다.
① 구매자가 테스트 결제 화면에서 에스크로를 선택하고 본인이 받을 수 있는 이메일을 입력합니다.
② 테스트 결제 후 결제사 상태를 조회합니다. 보관 확인은 토스의 useEscrow 및 escrowKey를 기준으로 합니다.
③ 구매자가 실제로 물품을 받았을 때 수령을 기록하고, 판매자가 직접 전달(DIRECT)을 등록합니다.
④ 구매확정은 토스 메일에서 구매자가 처리하거나 계약 조건에 따라 자동확정됩니다. 토스가 CONFIRMED로 회신한 뒤 확정 표시가 나옵니다.
테스트 환경에서도 토스의 구매확정 메일이 실제로 발송될 수 있습니다. 모의 장부와 토스 에스크로는 별도 흐름입니다.

지급대행 계약 및 실제 등록한 법인 테스트 셀러가 있다면 TOSS_TEST_PAYOUT_LOOKUP_ENABLED=true로
관리자 화면의 ‘테스트 지급 내역 조회’를 엽니다. 실제 등록한 셀러 ID와 참조번호를 프로젝트 판매자에게 연결하고,
외부에서 생성한 테스트 지급 ID를 주문에 연결합니다. refPayoutId는 이 프로젝트의 주문번호와 같아야 합니다.
조회 시 수취 셀러, 금액, 통화 및 확인된 테스트 에스크로 거래를 검사합니다. 이 앱은 토스에 지급을 요청하지 않습니다.
토스 안내상 테스트 셀러 등록은 유효한 법인사업자 번호가 필요합니다. 학생 개인 계좌 정산 성공으로 발표하지 마세요.
토스 안내: https://docs.tosspayments.com/guides/v2/escrow  /  https://docs.tosspayments.com/guides/v2/payouts
